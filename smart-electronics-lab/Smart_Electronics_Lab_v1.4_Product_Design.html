0. What changed in v1.4

v1.4 adds a no-code product architecture on top of v1.3's three-kit ladder. The design problem: none of the three kits should require the ordinary learner to write or compile code to reach their main milestones. Coding remains possible and teachable, but it moves to an explicit, optional Developer Mode path (§20) rather than being the default way to get a kit working. v1.4 changes nothing about the kit ladder, BOM, hardware design, or lesson content decided in v1.3 — it adds the user-facing and firmware-delivery layer that sits on top of all three kits.

2. The MVP, stated plainly NEW

The first MVP is not SDR. It is not a 15-inch screen. It is not a proprietary smart breadboard.

The first MVP is one guided LED/resistor lesson where the Elecrow tutor reads measured current from the INA219 and responds correctly — a pass message on expected current, a fail message on an open circuit or an out-of-range reading.

Everything else in this document is what gets built after that one lesson works end-to-end.

5. Kit 1, Part 1: hardware design

3.3V logic warning: the Elecrow / ESP32-S3 GPIO and I2C pins are 3.3V logic. Do not connect 5V directly to any GPIO, I2C, UART, touch, display, or expansion pin unless the Elecrow documentation explicitly states that pin is 5V tolerant. The breadboard may use 5V for isolated LED/resistor experiments that never touch an Elecrow pin — but any circuit connected to Elecrow data pins defaults to 3.3V logic.

Mounting answer

The Elecrow display does not need to sit in the breadboard. It sits next to the BB830 on the desk or mat, then connects to the breadboard through its GPIO/I2C connector or pigtail. The breadboard is for temporary circuits. The display is the tutor and controller.

Smart board answer

Do not start by designing a proprietary smart breadboard. Start by making the power path smart. If the Elecrow can read voltage and current from an INA219 sensor over I2C, the lesson engine can compare expected and measured behavior.

  • The INA219 must be in the measured load's current path. If the load can draw current through any path that bypasses the INA219, the software cannot detect that current.
  • The Elecrow, INA219, and breadboard circuit must share a common ground.
  • The INA219's I2C logic side should be powered at the Elecrow-safe logic voltage — normally 3.3V — unless the Elecrow's I2C pins are confirmed 5V tolerant.

6. Kit 1, Part 2: internet-radio capstone NEW

Kit 1's "wow" moment is the first time the learner hears sound from something they assembled. This section assumes the Elecrow does not expose a clean, confirmed audio path, and routes the radio capstone through a second, dedicated ESP32 audio module instead — so the capstone never depends on an unconfirmed Elecrow capability.

Why a second module, even if Elecrow audio turns out fine: the second ESP32 audio module is not only a workaround for the Elecrow's uncertain audio path. Even if the Elecrow turned out to support clean audio output, Kit 1 Deluxe would likely still keep audio on a separate module: it keeps the tutor/control-head firmware free of streaming and decode workload, and it turns the radio capstone into a distinct, sellable tier (Kit 1 Deluxe over Kit 1 Standard) rather than a feature silently folded into the base unit.

Command protocol, generalized EXTENDED

The v1.1/v1.2 USB-serial JSON-per-line direction carries forward, generalized to cover audio commands (and, in §13, SDR commands) alongside the original knob/touch/button events:

Any step with requires_power_off_before_step: true makes the engine render a standard interstitial — "Disconnect power before changing this wiring. Press when power is disconnected." — before the step prompt. measurement_source distinguishes a human-read value (user_meter, usb_meter) from a software-read one (ina219, gpio_adc). warning_threshold / hard_fault_threshold / max_safe_current_mA separate "this looks off" from "this is dangerous" from "this lesson's safe ceiling," and are what L10's controlled fault drill manipulates without ever exceeding the circuit's real safe operating current.

Developer mode

Connect the Elecrow to a Mac or PC with a USB-C data cable. Use PlatformIO first if possible, or Arduino IDE if following Elecrow examples. Upload firmware over USB-C. The Kit 1 Part 2 audio module is developed the same way, as a second, independent Arduino/PlatformIO project.

User mode

Later, the device should update over Wi-Fi. A user would choose a lesson pack from a menu and the device would download content. This is not Kit 1 work.

Storage plan

Do not buy a microSD card yet. The Elecrow listing specifies 16M flash, UART, I2C, and FPC expansion, but does not advertise a microSD slot. The v1 plan:

  • Firmware uploaded over USB-C during development.
  • Lesson content (the schema above) compiled into firmware or stored in internal flash using LittleFS or an equivalent ESP32 filesystem.
  • Wi-Fi content updates deferred until the lesson engine is stable.
  • External SD only if hardware inspection confirms a usable slot, or if an SPI SD module is added later.

Avoid excessive flash writes

Live measurements (voltage/current readings during an active lesson) stay in RAM. Only lesson completion, fault summaries, and calibration records get persisted to flash. High-frequency writes of live sensor data would shorten flash life for no benefit.

Lesson engine

The correct architecture is a small lesson engine, not custom firmware per lesson. The engine knows how to display a step, draw a wiring diagram, wait for a knob press, ask a question, read the current sensor, compare expected values against the schema above, and advance.

8. Smart Power Module path

V0: Visible power

Use the Plugable USB-C meter. The learner reads voltage, current, and watts manually. Sufficient for Ohm's law lessons.

Measurement scope caveat: the Plugable meter measures the USB-C power path, not necessarily the exact branch current of a breadboard circuit. The meter is excellent for visible V/A/W intuition; the INA219 is the correct path for software-readable, circuit-specific measurement.

V1: Software-observed power

Wire the INA219 in series with the breadboard load, connected to the Elecrow via I2C, following the topology in Figure 3 (§5). The lesson engine reads current and voltage directly.

V1 fault behavior: on over-current or out-of-range read, the lesson engine (1) shows a full-screen red fault banner, (2) displays the explicit instruction "Disconnect power now," and (3) logs the fault event (timestamp and reading, persisted). There is no automatic cutoff at V1 — the learner is the disconnect mechanism. L10 (§11) gives the learner deliberate, supervised practice with this exact banner before they can encounter it by accident.

V2: Protected smart module

Design a custom board with USB-C input, current limiting, measurement, fault reporting, and a safe disconnect circuit. This becomes the commercial product core, and is the first version where "warn" can become "warn and cut."

V3: Row-aware smart breadboard

Only after the power module works, explore sensing rows or continuity. This is much harder and should not be the first product.

10. Safety scope

  • Kit 1 is low-voltage DC only: 3.3V (default) and 5V (isolated experiments only) breadboard circuits.
  • No AC mains. No wall outlet experiments. No exposed lithium battery charging experiments.
  • The Elecrow / ESP32-S3 GPIO and I2C pins are 3.3V logic. Never connect 5V directly to a GPIO, I2C, UART, touch, display, or expansion pin unless the documentation explicitly states 5V tolerance. This applies equally to the Part 2 audio module's UART link.
  • Assume beginner mistakes. Use current limiting, start with higher resistor values, and disconnect power before rewiring — practiced directly in L1 and enforced structurally via requires_power_off_before_step (§7).
  • The smart module should detect over-current and shut off or warn before damage occurs. At V1, the off-the-shelf module can only warn (§8); L10 gives the learner practiced, supervised exposure to that warning before it can happen unsupervised.
  • The audio module and the Elecrow must share a common ground if linked by UART or I2C; the speaker/amp side carries no GPIO-safety concerns of its own since it never touches Elecrow pins directly.

11. Kit 1 lesson sequence EXTENDED, L12–L13 NEW

L0: First boot validation — before any breadboard wiring: load a vendor example over USB-C and confirm, in order: display output, capacitive touch response, knob rotation, knob press, and a successful USB-C firmware upload. Record the exact board definition, library versions, and example sketch name used.

L1: Power-off habit — the screen asks the learner to disconnect power, then walks through placing/removing a single jumper, then reconnect. No measurement yet.

L2: LED with resistor: Build a simple LED circuit at 3.3V with a red or yellow LED. The screen teaches polarity, current limiting, and expected current (target <5 mA).

L3: Change the resistor: Swap 1k, 470Ω, and 330Ω resistors at 3.3V. The screen asks the learner to predict brightness and current before measuring.

L4: Series resistance: Place two resistors in series and measure lower current.

L5: Parallel branches: Build two LED branches and observe total current increase.

L6: Button input: Wire a pushbutton and pull-down resistor. The display changes when the button is pressed.

L7: Potentiometer: Use a 10K pot as a voltage divider. Turn the pot and watch analog voltage change.

L8: Software-controlled LED: Use the Elecrow to drive an LED through a resistor. Then map knob position to brightness.

L9: Smart measurement: Insert the INA219 into the load path (Figure 3). The display compares expected and measured current.

L10: Controlled fault-screen drill — uses the same safe circuit already on the board, well within the current-limit table. The lesson temporarily lowers its own thresholds far below the circuit's actual safe current, so the existing, unmodified, safe current trips the red fault banner. No real over-current is ever created.

L11: Transistor switch: Use a transistor to drive a buzzer or higher-current LED path from a GPIO pin.

L12: Audio module bring-up NEW — wire the second ESP32-S3 + MAX98357A + speaker on the breadboard, flash a minimal Arduino sketch, and confirm a test tone plays. This is purely a hardware/firmware checkpoint — no Wi-Fi yet.

L13: Internet-radio capstone NEW — connect the audio module to Wi-Fi, fetch a small JSON station list (folding in v1.1/v1.2's old "Stage 2a" Wi-Fi/API teaching), select a saved favorite using the Elecrow knob, and send play_station over the UART link. Success is audio from the speaker. This is the Kit 1 finale.

12. Example on-screen lesson flow

  1. Screen: Find a 330Ω resistor and a red or yellow LED. Press the knob when found.
  2. Screen: Place one end at row A10 and the other at row A15.
  3. Screen: Place LED long leg at A15 and short leg to the ground rail.
  4. Screen: Disconnect power before connecting the 3.3V rail through the resistor path.
  5. Screen: Turn power on. Expected current is about 3 to 5 mA at 3.3V with a red or yellow LED.
  6. Screen, V0: Read the Plugable meter and enter or select the closest current.
  7. Screen, V1: Sensor reads 3.9 mA. Correct. Press to continue.
  8. Screen: Replace the 330Ω resistor with 1k. Predict whether the LED gets brighter or dimmer.

Researched receiver and software

RTL-SDR Blog V4 is the recommended receiver: it replaced the older R820T2 tuner with an R828D tuner plus an internal triplexer, giving native HF reception (500 kHz–1.766 GHz continuous) without an upconverter, and better filtering against FM-broadcast overload than the V3. SDR++ is the recommended first-success waterfall software: it is modern, cross-platform, and runs well on both Pi 4 and Pi 5 with a lighter resource footprint than GQRX. GQRX remains a documented fallback for users who prefer its simpler, more minimal Linux-native interface.

16. Product concept

What is distinctive

Most electronics kits give instructions. This system gives feedback: it teaches, observes, and reacts. The device does not merely say what to build. It observes voltage and current and tells the learner what likely happened — and that same teach/observe/react loop is what makes Kit 1's radio capstone land as a "wow" moment rather than a generic feature checkbox: the learner spent Kit 1 Part 1 quietly wiring and being corrected, and the payoff is that the thing they built makes sound.

Why this can be a product

The first product does not require a proprietary breadboard, an SDR receiver, or a 15″ screen (§2). The first sellable unit is a smart USB-C power and measurement module, plus an ESP32 display tutor, plus a standard BB830 — Kit 1, Part 1, full stop. Kit 1 Part 2, Kit 2, and Kit 3 are upsells to a working core, not prerequisites for it.

Product realism note: the likely first sellable product is not a smart breadboard, an SDR kit, or a workstation. It is a smart USB-C power and measurement module, paired with a standard BB830, paired with an ESP32 display tutor, with lessons as structured content packs (§7's schema). Kit 1 Part 2's radio capstone is the first upsell; Kit 2 and Kit 3 are further upsells for a smaller, more advanced segment of that same customer base.

Course packs

The same hardware could support course packs: Electronics Fundamentals, Internet Radio, Amateur Radio, SDR Basics, Sensors, Home Automation, and Robotics. With the lesson schema in §7, each course pack is a set of schema files plus assets, not a firmware fork. Internet Radio is now Kit 1's own course pack rather than a Stage 2 appliance feature; SDR Basics becomes Kit 2/3's course pack.

Commercial risk

The difficult parts are not the first hardware. The hard work is curriculum design, safe fault handling, reliable connectoring, and making lessons resilient when beginners miswire circuits. The lesson schema and the V1 fault behavior (§7–8) are concrete artifacts against that risk, not just statements of it.

19. Future hardware convergence (v2) NEW

Not a v1.3 dependency: nothing in this section changes or delays the near-term plan. v1.3 stays off-the-shelf and buildable today — Elecrow + breadboard for Kit 1 Standard, plus a second ESP32 + MAX98357A + speaker for Kit 1 Deluxe. This section documents a future direction, gated on proving the MVP first. It is not a design task to start now, and it has no BOM line in §15.

Kit 1 Deluxe currently splits its functions across two boards: the Elecrow (tutor, control head, knob/touch UI) and a second ESP32 audio module (Wi-Fi streaming, I2S decode, amplification). That split is the right v1 architecture — cheap, off-the-shelf, and it keeps each board's firmware simple. It is also, by construction, a preview of a single future device.

Trigger condition

Once the MVP is proven — the lesson engine, the smart measurement loop (INA219 path, §5/§8), and the internet-radio capstone (§6) all working end-to-end on off-the-shelf parts — it becomes worth designing a custom dial/display module that converges what the Elecrow and the second ESP32 audio module do today into one board.

What the custom module should include

  • Rotary control (carried from the Elecrow's knob interaction model).
  • Touchscreen (carried from the Elecrow's capacitive display).
  • A protected expansion connector, so breadboard/sensor wiring mistakes can't easily damage the main board.
  • USB-C power and data, for both charging/power and firmware updates.
  • A built-in smart-measurement interface (the INA219-class current/voltage sensing path, §5/§8), instead of routing it through an external breakout.
  • A clean audio path — an onboard codec, an integrated I2S amplifier, or at minimum a speaker connector — so the radio capstone no longer needs a second physical board.

20. User paths: Use Mode, Configure Mode, Developer Mode NEW

The design problem this section answers: the product cannot require the ordinary learner to write code to complete Kit 1 Part 2, Kit 2, or Kit 3. Coding should remain possible, and eventually teachable, but it must not be the default completion path. Without this distinction, the project is an open-source build; with it, the project is a guided learning product.

Hard requirement: a learner must be able to complete the main milestones of Kit 1, Kit 2, and Kit 3 without writing code. The product may teach what the code is doing, and may offer a later "learn to modify the firmware" branch, but the default user should never need to open PlatformIO, edit C++, debug libraries, or compile firmware manually to reach a kit's milestone.

Path A: Use Mode — default, no coding

The user installs prebuilt firmware through a browser-based installer (§22) and follows guided instructions. No step in either flow below requires writing or compiling code.

Kit 1:

  1. Plug the Elecrow rotary display into a computer using USB-C.
  2. Open the Smart Lab web installer.
  3. Click "Install Tutor Firmware."
  4. Plug in the second ESP32 audio board (Kit 1 Deluxe only).
  5. Click "Install Radio Audio Firmware."
  6. Follow the Elecrow screen to configure Wi-Fi, test hardware, build lessons, and play internet-radio audio.

Kit 2 / Kit 3:

  1. Flash or boot a prepared Raspberry Pi / mini PC image, or run a packaged installer.
  2. Plug in the RTL-SDR receiver.
  3. Open the preconfigured SDR application.
  4. Confirm the waterfall display.
  5. Connect the Elecrow control head.
  6. Turn the Elecrow knob and confirm a real SDR parameter changes — frequency, zoom, gain, or preset.

Path B: Configure Mode — no coding, editable settings

Configure Mode lets the user customize the product without programming it. Configurable items include Wi-Fi credentials, the station list, volume defaults, lesson-pack selection, device name, measurement calibration values, SDR presets, local weather/location settings, the ham repeater database source, and display preferences.

Configuration runs through one or more of: on-device menus, a local web interface served by the device, a JSON/YAML config file (§25), a browser-based setup page, or serial console commands as a fallback only.

Path C: Developer Mode — coding allowed

Developer Mode is for Bob, Claude, Codex, maintainers, and open-source contributors. It uses PlatformIO, the Arduino framework for ESP32 first, the GitHub repository, serial logs, the unit-testable lesson schema files, firmware builds, and release binaries — with ESP-IDF only if later needed. Developer Mode is documented (§21, §23), but it is never required to complete a user-facing kit milestone.

22. Browser-based flashing NEW

The preferred no-code flashing path is a web installer — a tool in the ESP Web Tools / ESP Launchpad class. Arduino IDE and PlatformIO are not required for Use Mode.

Implementation requirements:

  • Host the firmware binaries and a manifest/configuration file.
  • One install button per supported board.
  • Clear board-compatibility display.
  • A "known good firmware" fallback build.
  • Version numbers and release notes on every build.
  • A documented recovery procedure.
  • A serial log viewer or simple diagnostic mode, if the chosen web flasher supports it.
Platform caveat: browser-based ESP flashing requires a desktop browser with Web Serial support. iPhone/iPad should not be assumed to work for flashing. Mobile devices are fine for reading instructions, but are not the primary firmware installer.

29. Support, recovery, and flash-storage behavior NEW

Use Mode (§20) must assume some users will miswire hardware, flash the wrong firmware, lose Wi-Fi credentials, or use a power-only USB-C cable. Troubleshooting should be productized, not improvised:

  • Known-good firmware recovery and an "erase and reinstall" path.
  • Serial log access for troubleshooting, where the web flasher supports it (§22).
  • A visible version number on each device.
  • Self-test screens: hardware, audio, INA219, and Wi-Fi.
  • A "safe mode" boot option, if feasible.

Flash-storage behavior carries forward from §7 unchanged, restated under the no-code framing: live measurements stay in RAM; only lesson completion, summaries, calibration, and settings persist. Lesson data for v1 lives in the internal flash filesystem or is firmware-embedded — no microSD is assumed for the Elecrow. Browser flashing (§22) is the default firmware update path for early product versions; Wi-Fi lesson-pack download remains future work (§7).

Extends §13: the no-code user path must use one of a prepared Raspberry Pi image, Raspberry Pi Imager-compatible instructions, a packaged install script, a preconfigured SDR++ profile, or a preinstalled serial bridge service. Kit 2/3 users should not need to compile SDR software.

The Pi/mini PC image should include: SDR++ (or the chosen SDR application, §13), RTL-SDR support, a default waterfall profile, the serial bridge listener for the Elecrow, sample frequency presets, a first-run wizard, and recovery instructions.

31. Product identity statement NEW

Smart Electronics Lab is not a coding kit. It is a guided electronics learning system with an optional developer track. The default learner experience is: install firmware, follow the tutor, build the circuit, observe the measurement, and unlock the next capability. Coding is a later branch, not a prerequisite for success.
